# 内存优化记录（2026-10-15）

目标：单浏览器容器 200 MB 以内。**本轮尚未达到该目标，也不保证任意第三方网页的内存上限。**

## 实现

- 流式 DOM 更新复用未变化的节点记录，避免每次修改都保留另一份完整样式数据。
- 历史快照从 8 份减至 2 份。客户端落后更多版本时自动回退到完整快照，保持恢复正确性。
- 关闭会话时释放当前及历史快照。
- Chromium 禁用 GPU 加速和前进后退页面缓存，使用体积优先的 V8 策略；进程数量参数只是提示，不关闭站点隔离和沙箱。
- 多账户引擎镜像的 Node V8 老生代上限为 128 MiB、半空间为 2 MiB。这不是容器总内存上限，超大 DOM、IndexedDB 或并发页面仍可能触及 Node 堆上限；可按负载通过 NODE_OPTIONS 调整。

## 对照结果

在同一主机依次运行隔离测试容器，使用相同基础 Chromium 镜像、页面与 1 GiB 容器限制。每个场景采样 12 次，间隔 1 秒。指标为 memory.current 减去 inactive_file，与 Docker 工作集读数口径接近；不是进程 RSS 相加。

| 场景 | 原版中位数 / 峰值 | 优化版中位数 / 峰值 |
| --- | --- | --- |
| 内置简单页面 | 264 / 266 MiB | 251 / 252 MiB |
| 500 行文本、每 200 ms 更新末行 | 370 / 394 MiB | 292 / 341 MiB |

动态场景中位数下降约 21%。原始采样见 [memory-benchmark.json](memory-benchmark.json)。这只是短时合成负载对照，不代表 ChatGPT、Claude、媒体网站或多窗口的峰值，也不能替代长时间压力测试。

41 项单元测试及 16 项浏览器回归通过，覆盖输入、流式更新、跨源嵌入、资源、媒体、重连与状态保存恢复。额外强制垃圾回收的收益不明显，未应用于正式运行。

## 重现测试

在仓库根目录执行 npm ci、npm run build。使用 esbuild 将 scripts/benchmark-memory.ts 打包为 Node ESM（packages=external），然后复制到专用的引擎测试容器中运行。该容器需包含 dist、生产依赖和可运行沙箱的 Chromium；以非 root 用户运行，并加载 deploy/chromium-seccomp.json。脚本只打开内置测试页面，不访问用户账户或外部网站。

优化版 Node 参数为 --max-old-space-size=128 --max-semi-space-size=2；基线使用优化前源码和默认 Node 参数。不要在共享应用容器或宿主机直接比较 cgroup 总内存，它会包含同一 cgroup 中其他进程的开销。完整样例采样脚本位于 scripts/benchmark-memory.ts。


## 交互与处理延迟优化（0.8.1）

- 连续滚动改为每 45 ms 合并发送最新位置，不再等滚动停止。多个滚动区域分别记录；点击和拖拽前先提交待发送的滚动，避免远端位置滞后。
- 页面差分直接比较结构，减少完整节点 JSON 字符串的分配。
- 图片、媒体及 CSS 资源从专用字段查找，不再扫描整段正文和输入内容。
- 手动缩放倍率同步到渲染页面，修复缩放后拖拽位置不准。适配屏幕会恢复 100%，并修改远端视口大小。

2000 个节点、每个节点 30 个样式字段的合成微基准，5 轮、每轮 30 次，中位数：差分由 13.59 ms 降至 8.68 ms，资源查找由 7.79 ms 降至 0.77 ms。见 [原始数据](responsiveness-benchmark.json)。这不是整站端到端延迟，真实效果取决于网页、客户端和网络。

可用 `node --expose-gc --import tsx scripts/benchmark-responsiveness.ts` 重现。脚本包含上一版对照算法，并校验两种算法在该负载下的输出一致。

连续滚动回归测试在旧版失败，新版约 109–115 ms 观察到两个远端滚动区域开始同步。内存复测：简单页面中位数 256 MiB，动态页面 298.5 MiB，本轮未观察到常驻内存进一步显著下降，200 MB 目标仍未达成。

本轮类型检查与构建通过，43 项单元测试及 20 项浏览器回归测试通过。覆盖连续滚动、输入防回退、触控、拖拽、资源加载、媒体、手动缩放及视口适配。线上账户页与运行中的工作容器健康检查通过。

## 异步渲染与慢客户端流量控制

进入浏览器页面时，大批节点的属性、样式和层级更新可能长时间占用客户端主线程。渲染器现在按约 8 ms 的工作片段主动让出执行权，让浏览器有机会处理工具栏、输入和绘制；这不是对每个任务耗时或每帧帧率的保证。

客户端一次只提交一个画面更新，等待渲染器确认后再提交下一次。等待期间合并连续版本的增量，保留最终节点状态和删除操作；遇到版本断层重新同步。新连接的标识使旧渲染确认无法推进新会话队列。

WebSocket 客户端启用画面流量控制后，服务端在收到渲染确认前暂停后续画面推送，随后从当前页面状态生成增量或完整快照，不按历史更新逐条补发。点击、键盘输入的执行和确认、对话框消息及心跳独立于画面确认。旧客户端仍可使用原协议，HTTP 备用连接继续工作。

WebSocket 上连续的滚动、悬停、视口变更可在 8 ms 窗口内合并同一目标的相邻更新。点击、按键及输入会立即发送，并先发送排在它们之前的操作；不重排有顺序依赖的输入。

资源仍使用独立下载通道和客户端缓存。减少的是渲染及传输积压，网络往返、远端网页执行和 Chromium 内存仍然存在，不能据此承诺单容器 200 MB 或所有设备不再卡顿。

验证包括 50 项单元测试、26 项浏览器回归，以及跨页面版本边界修正后的 2 项专项复测。专项测试用 1,800 个节点验证渲染期间浏览器任务仍可执行，并模拟暂不确认画面的 WebSocket 客户端，检查操作确认、最新状态同步、错误确认忽略及重新同步。
